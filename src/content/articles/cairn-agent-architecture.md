之前看到 [Cairn](https://github.com/oritera/Cairn) 的介绍，就想看看它到底是怎么组织 Agent 工作的。平时给 Claude Code 一个任务，它自己也会读文件、执行命令、根据结果继续操作，那 Cairn 加在外面的这一层又做了什么？

顺着项目看了一圈之后，感觉它有意思的地方，就是把这些任务之间的关系整理得比较清楚。这篇先记一下我对它结构的理解，以及几个觉得以后自己写项目时可以学的地方。

这里看的公开版源码是 `8e7e0ea`。只讨论这份实现，作者另外介绍的新版本先不混在一起。

## 先看谁负责什么

项目主要分成 Server、Dispatcher 和 Worker 三部分。

| 组件 | 主要职责 |
| --- | --- |
| Server | 保存任务图，提供 API，管理任务领取、心跳和状态 |
| Dispatcher | 按代码规则检查项目状态，选择任务和 Worker，解析并提交结果 |
| Worker | 运行 Agent，读取提示词和上下文，按任务使用工具，返回结果 |

刚开始我把它理解成“一个主 Agent，带着另一个 Agent 做事”。后来才发现，**Dispatcher 本身是普通的 Python 调度程序**。需要模型判断的部分，比如考虑下一步探索方向，会被包装成任务交给 Worker。

```text
Server：保存状态
    ↕ API 读写
Dispatcher：选择任务、组织上下文、提交结果
    ↕ 提示词与执行结果
Worker：调用模型和工具，开展工作
```

Worker 支持 Claude Code、Codex、Pi 等后端。所以这里的 Worker 也不一定代表一个从头到尾一直在线的固定角色，更接近一套执行配置，以及按这套配置启动的具体任务。

## 用任务图记录走到了哪里

Cairn 用了几个很直观的概念：

| 概念 | 可以怎么理解 |
| --- | --- |
| Origin | 起点，已经知道什么 |
| Goal | 想达到什么结果 |
| Fact | 已经记录下来的发现 |
| Intent | 基于已有发现，准备探索的方向 |
| Hint | 人补充的信息、约束或者判断 |

主要关系就是：

```text
一个或多个 Fact → Intent → 新 Fact
```

比如已经发现某个功能，就基于它提出一个需要验证的方向；执行之后，再把结果记下来，供后面继续判断。

这里我觉得比较好的地方是，把“已经发现了什么”和“接下来准备试什么”分开了。后面回看时，能看出一个方向为什么会被提出、执行后得到了什么，也能看到哪些方向还没有做。

不过 Fact 这个名字也需要留意。它保存的是 Agent 提交的结果描述，**不代表 Server 已经独立验证过里面每个结论**。图能把过程组织起来，结果是否可靠还是要看证据。

![Cairn Project 3 的任务执行图：多个探索方向从已有发现展开，项目状态为已停止](/articles/cairn-agent-architecture/project-003-task-graph.png)

这是之前一次实践留下的任务图，可以看到探索方向会分叉，也会基于已有结果继续往下走。截图时项目已经停止，图中仍有未完成方向，用来看看它怎样记录过程。

## Bootstrap、Reason 和 Explore

这三个是任务类型，可以由同一套 Worker 配置执行，不是三个固定身份的 Agent。

**Bootstrap** 先直接尝试解决。如果问题比较简单，这里就可能完成；如果正常结束后还没有解决，就留下发现继续推进。

**Reason** 读取当前任务图，判断已有证据是否满足 Goal；如果还需要探索，就提出一个或多个 Intent，也可能暂时不新增方向。

**Explore** 执行其中一个 Intent，把本次发现汇总回来。

```text
Origin、Goal、可选 Hint
    ↓
Bootstrap：先直接尝试
    ├─ 已解决 → 完成
    └─ 未解决，留下 Fact
                  ↓
                Reason
                  ├─ 已满足 Goal → 完成
                  └─ 提出 Intent
                         ↓
                       Explore
                         ↓
                       新 Fact
                         ↓
                    再次 Reason
```

这是正常主线，Bootstrap 也可以在创建项目时关闭，直接从 Reason 开始。

一个 Fact 后面可以展开多个方向，多个 Intent 是排队还是并行，则由全局、项目以及 Worker 自身的并发限制共同决定。

它也不是必须把这一批方向都做完，才能再考虑下一步。某个方向产出新 Fact 后，就可能触发新的 Reason，重新判断目标是否已经达到。能不能马上运行，还要看有没有可用名额。

这个设计比较适合路径未知的探索：先基于现有信息选方向，得到新结果后再调整。相应地，Goal 怎么写就很重要，“找到一个问题”和“完成指定范围的检查”，应该有不同的停止条件。

## 外面一层调度，里面还有一层循环

这是我看到后面才理清的地方。最开始以为，一次 Worker 任务就是整理好提示词，发一次模型请求，拿回回答就结束了。

但项目可以启动 Claude Code CLI 这样的 Agent 执行器。它本身就会管理会话，在内部反复请求模型、执行工具、把工具结果提供给后续模型调用，直到返回最终结果。

所以这里其实有两层循环：

```text
外层 Cairn：
看任务图 → 提出方向 → 调度任务 → 保存结果 → 再判断

内层 Agent 执行器：
请求模型 → 执行工具 → 观察结果 → 继续行动 → 返回总结
```

一个 Explore 可以包含很多动作和模型请求，Dispatcher 不需要一条命令一条命令地指挥它。

一次任务内部有自己的会话上下文，不同任务之间则主要通过任务图重新获得信息，工作目录中的文件也可能继续使用。这样就不必始终带着整个项目的完整对话历史往下走，但重要信息如果没有被保存，后续任务也可能不知道。

**Cairn 复用了已有 Agent 执行器的能力，在外面处理任务之间的衔接。**这个边界我觉得挺值得参考，不需要什么都从头写一遍。

## 模型输出怎么接到数据库

Worker 最后按提示词返回结构化结果，例如 Explore 的正常输出：

```json
{
  "accepted": true,
  "data": {
    "description": "本次确认的新增发现，以及必要的证据位置。"
  }
}
```

Dispatcher 解析 JSON，检查格式，再通过 API 写回 Server。

项目 ID、Intent ID、Worker 名称都由程序持有，模型只需要返回结果内容。Server 分配新 Fact ID，插入结果，再更新当前 Intent 的结果端。

```text
已经存在：Fact A → Intent
完成后：  Fact A → Intent → Fact B
```

一次 Explore 内可以得到多个发现，但正常汇总后写成的是一个 Fact 节点，不是每次工具输出都生成一个节点。较大的证据可以放在文件里，由描述引用。

这就把模型比较开放的输出，接到了明确的程序流程里。不过格式校验只能保证 JSON 能被处理，无法保证描述里的结论正确。后面继续 Reason 时又会使用这些摘要，所以总结质量也会影响后续判断。

## 几个想留下来的设计

看完之后，最想留下的是：**先把任务状态设计出来，再考虑提示词怎么写。**

之前想到类似项目，很容易先纠结给 Agent 什么身份、怎么写一段厉害的提示词。但任务归谁、结果保存在哪里、什么时候继续、什么情况算结束，这些也得有明确的结构。Cairn 用相对少的概念把这些事情串了起来，读的时候也比较容易沿着实际任务去找对应代码。

第二点是，分清哪些地方需要模型判断。提出探索方向需要理解当前情况，而任务 ID、关联关系、并发限制和数据库写入，用程序处理就很合适。不必再让一个模型去管理所有琐事。

第三点是对长任务的管理。并发、心跳、超时、取消、任务释放、兜底汇总，这些看起来没有推理过程那么显眼，但任务卡住、进程退出或者结果格式不对的时候，就得靠它们处理。这里目前看过主要流程，失败恢复的细节还没有逐个读完。

如果以后自己写类似项目，我会先做到一个任务能执行、结果能保存、失败能看见、过程能回查，再考虑多方向和并发。输出结构里也尽量分清观察、推断和已经验证的结果，并且能够找到对应证据。

这轮先看到这里。能把一次任务从调度追到执行，再追到 API 和数据库写入，已经有不少可以带走的东西了。
