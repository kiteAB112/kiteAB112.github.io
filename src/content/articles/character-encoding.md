同样是很久之前做过类似笔记的，关于计算机编码相关，不过今天再看之后才发现原来还有些地方之前一直以为明白了但是没明白。

基本了解之后，下面这个就可以很快速的了解整个发展流程了
```bash
计算机只认识字节
        ↓
ASCII 出现，用 0~127 表示英文和控制字符
        ↓
各国文字不够用，开始扩展 0x80~0xFF
        ↓
中文出现 GB2312、GBK、GB18030
日文出现 Shift_JIS
繁中出现 Big5
        ↓
各国编码互不兼容，乱码频繁
        ↓
Unicode 统一给全世界字符编号
        ↓
UTF-8 成为最主流的 Unicode 存储方式
```


这里需要注意的一个点就是 `Unicode` 与码点，`UTF-8` 与编码，之前都没听过码点这个概念，也就展现了之前确实不够了解，也就是 `Unicode` 其实相当于只是给世界上每个字符做了位置码点，确定了其唯一性，但是并没有规定实际编码写进计算机是什么方式，这些编码工作就是类似 `UTF-8` 指定一些编码规则，然后在写进计算机的时候就可以规范化。

### 字符、码点、编码、字节

#### 字符
人类看到的符号：

```
A
中
你
😀
```

#### 码点
Unicode 给字符分配的编号：

```
你 = U+4F60
```

#### 编码
把码点变成字节的规则：

```
UTF-8
UTF-16
GBK
Big5
```

#### 字节
实际存储的数据：

```
E4 BD A0
```


### 举例讲解

```bash
Unicode     = 字典，规定“你”这个字的编号是 U+4F60

UTF-8       = 一种打包规则，把 U+4F60 打包成 E4 BD A0

UTF-16      = 另一种打包规则，把 U+4F60 打包成 4F 60 / 60 4F

UTF-32      = 最直白的打包规则，把 U+4F60 打包成 00 00 4F 60
```

#### 写入
```bash
人看到的字符
   ↓
Unicode 码点
   ↓
UTF-8 / UTF-16 / UTF-32 编码
   ↓
硬盘/网络里真正保存和传输的字节
```


读取显示
```bash
硬盘/网络里的字节
   ↓
按 UTF-8 / UTF-16 / GBK 等规则解码
   ↓
Unicode 码点
   ↓
显示成字符
```

### 扩展

#### win中的换行为何独树一帜

这个问题可以从**打字机的物理动作**讲起，Windows 的 `CRLF` 就是历史包袱留下来的。早期不是屏幕显示文字，而是类似电传打字机、打印机这种设备，所以实际上想打印下一行，需要做两个动作：
```bash
动作 1：把打印头移回本行最左边 -- CR(Carriage Return) 回到最左边 -- 0x0D
动作 2：把纸往上卷一行 -- LF(Line Feed) 换下一行 -- 0x0A
```

由此在 win 里面就留下了换行是 `\r\n` = `0x0D 0x0A`


后来进入 <mark>Unix 时代</mark>后，系统设计者觉得：

> 文本文件里的“换行”应该是一个逻辑概念，不应该还保留两个机械动作

最终设计者选定了 `LF` ，也就是 `\n` = `0x0A` 作为换行，平时在 linux 中见到的也多数是

```bash
Hello\nWorld
```

实际编码例子：

```bash
# Win 中
48 65 6C 6C 6F    = Hello
0D                = CR，回车
0A                = LF，换行
57 6F 72 6C 64    = World

# Unix 中
48 65 6C 6C 6F    = Hello
0A                = LF，换行
57 6F 72 6C 64    = World

```

这个关于 `LF` 和 `CRLF` 其实本人最常见的是 git 在使用过程中会碰到警告 `LF will be replaced by CRLF` ，这里涉及到的就是使用不同操作系统写代码，如果是 win 保存的话换行编码就是 `CRLF`，linux/mac 的话就会是 `LF` ，这样如果不做配置的话就会让 git 认为更改了很多内容，因为 git 本质是也是在检测编码后的不同点；

对此 git 也有相关配置

```bash
git config --global core.autocrlf true
git config --global core.autocrlf false
git config --global core.autocrlf input
```

| 配置  | 含义  |
| --- | --- |
| `true` | 提交时转 LF，检出时转 CRLF，适合部分 Windows 用户 |
| `input` | 提交时转 LF，检出不转换，适合 macOS/Linux |
| `false` | 不自动转换，完全保留原样 |


#### 幽灵 bit 位

它借用了“Java 里字符是 16 bit、byte 是 8 bit”这个差异；真正的问题不是编码转换，而是强制类型转换时发生了低 8 位截断。

下面直接原理 + 实际安全风险：

原因是程序员在写编码转换时候没有按照标准的来，写成了类似下面的造成最终并非编码转换而是造成了位截断
```bash
char ch = '陪';
byte b = (byte) ch; // 0x966A -> 0x6A，导致记得最开始无论是 C++ 还是 java 好像都经常这样直接强制转换来着
```

安全原因则是应用层做了过滤危险字符例如 `> < = \ / ?` 等等，但是如果出现上述代码我们就可以选取第八位显示我们想要的危险字符，高八位随便选即可，因为最后会被截断，这样也就会导致过滤的时候完全无用化



了解到最终原因之后才想到其实这里更贴合的单双字节编码案例应当是 sql 注入里面的那个


#### UTF-8、UTF-16、UTF-32 Diff

| 编码  | 是否变长 | 常见英文 | 常见中文 | Emoji | 是否兼容 ASCII |
| --- | --- | ---: | ---: | ---: | --- |
| UTF-8 | 变长，1~4 字节 | 1 字节 | 3 字节 | 4 字节 | 是   |
| UTF-16 | 变长，2 或 4 字节 | 2 字节 | 2 字节 | 4 字节 | 否   |
| UTF-32 | 定长，4 字节 | 4 字节 | 4 字节 | 4 字节 | 否   |


UTF-8 是现在最主流的文本编码。

它的核心规则是：

> **根据 Unicode 码点大小，用 1 到 4 个字节表示。**

常见情况：

| 码点范围 | UTF-8 字节数 |
| --- | --- |
| `U+0000 ~ U+007F` | 1 字节 |
| `U+0080 ~ U+07FF` | 2 字节 |
| `U+0800 ~ U+FFFF` | 3 字节 |
| `U+10000 ~ U+10FFFF` | 4 字节 |

举例上面的 “你” -- `U+4F60`，落在了3字节范围中，UTF-8 为三字节编码规定了这个模板，`x` 是存放码点数据的位置：

```bash
1110xxxx  10xxxxxx  10xxxxxx
```

其中共有 `4 + 6 + 6 = 16` 个数据位，把 `4F60` 转为二进制后按照 4,6,6 排序带入这个模板就是：

```bash
11100100 → E4
10111101 → BD
10100000 → A0
```

这些额外的前缀也有用途：**`1110` 告诉解码器“这是一个三字节序列的开头”，后面的 `10` 表示“这是接续字节”。** 读取时去掉这些前缀，把数据位拼回去，就能还原 `4F60`，再找到字符“你”


UTF-16 的核心规则是：

> **大部分常见字符用 2 字节；超过 `U+FFFF` 的字符用 4 字节，也就是代理对。**

它不是固定 2 字节编码，这点很重要。

常见情况：

| 码点范围 | UTF-16 字节数 |
| --- | --- |
| `U+0000 ~ U+FFFF` | 2 字节 |
| `U+10000 ~ U+10FFFF` | 4 字节 |


UTF-32 最简单粗暴：

> **每个 Unicode 码点固定用 4 个字节存**

没错，直接就是拿 Unicode 给好的码点写入，每个都占 4 字节，32 bit 
 



#### GBK 宽字节注入 / 宽字节 SQL 注入

GBK 是一种变长编码：

```
ASCII 字符：1 字节中文字符：通常 2 字节
```

在 GBK 里，某些高位字节，比如：

```
BF
DF
81~FE 范围内的一些字节
```

可能会和后面的一个字节组成一个汉字或其他字符

经典例子是攻击输入里放 `%BF%27` ，程序如果用了类似 `addslashes()` 的转义，会把 `'` 前面加上反斜杠，会变成 `%BF%5C%27` 对应字节 `BF 5C 27` 

此时数据库如果按 GBK 解释，前面两个字节可能会被当成一个合法的 GBK 双字节字符，反斜杠 `5C` 被前面的 `BF` “吃掉”了，剩下的 `27` 就重新变成了真正的 SQL 字符串结束单引号，也就是绕过了 `addslashes()`

数据库连接、客户端、服务端、表字段最好统一到 `utf8mb4` ，另外就是对于 `addslashes()` PHP 文档已经明确提醒：`addslashes()` 有时会被错误地用于防 SQL 注入，应该使用数据库专用转义函数或预处理语句

当然在有了预编译之后，其实很多问题都被解决了，无非就是老旧系统需要考虑了
